100G 数据，每批 10G
怎么安全地分批清理？

先把全部对象名单扫描入库，再创建一批、删除一批。scan 只做一次，重复 task create → purge；verify 可以稍后单独逐批执行，不阻塞下一批删除。

这是不可逆的物理删除。 工具清理 S3/MinIO piece 和本 SP 元数据，不发送链上 DeleteObject / Discontinue 交易，不停止链上计费，也不自动停 challenge。只能针对已授权的废弃数据；先在原 QA 环境完成小规模回归。

01先明确“100G / 10G”的意思

多个对象的逻辑总量
100 GiB
以名单中 payload_size 的合计为准
每个子任务目标
10 GiB
命令：--target-size 10GiB
预计子任务数量
约 10 批
不是固定 10 次循环，以实际任务为准

本例统一使用 GiB：1 GiB = 1,073,741,824 字节。若你说的 10G 是十进制 10 GB，请改用 --target-size 10000000000B；工具不接受 10G 或 10GB。

如果是一个 100G 的大文件，而不是多个文件共计 100G：工具不拆分一个 OID。即使目标设为 10GiB，这个超大对象也会独立组成一批，整对象处理；不能切成 10 个子任务。
  • 10GiB 是近似任务容量，不是硬上限。按 OID 顺序选完整对象，最后一个普通对象可使容量略超；超大对象独立成批。
  • --max-objects 10000 同时限制每批对象数。大量小对象可能先达到 10,000 个，任务不足 10GiB，批次数随之增加。
  • 逻辑容量 ≠ 本 SP 实际释放空间。primary 存完整段，secondary 存 EC 分片；不要拿本批 10GiB 直接对比云账单下降量。
  • 每个 SP 各跑一份；每个 SP 使用自己的配置和独立进度库。不是每一批新建一个数据库。

具体怎么选：10 个对象，每个 700MiB，目标 2GiB

按 OID 从小到大选择未分配对象，累计 payload_size 达到或超过目标就停止；不拆对象，也不挑大小精确凑数。假设 OID 为 1～10，且未触发对象数上限：

02准备环境与公共参数

  1. 确认运行的是新版工具。在现有测试环境更新并构建，不需要重建集群或切换存储后端。
  2. 由运维确认 challenge / attestation 风险已在所需范围处置，并停止目标数据的上传、更新、迁移和恢复回写。仅停本地一个进程，不等于全网风险解除。
  3. 核对本 SP 的 config、物理桶、BSDB/SpDB 和链 RPC；确认 BSDB 已同步。准备另一个逻辑 bucket 的对照对象，保存内容摘要用于前后核对。
  4. 为本轮清理建一个空的独立 MySQL 进度库，例如 limewire_purge_sp0_round1。工具会建立所需表，但不会替你创建数据库；不要使用业务库、另一个 SP 的进度库或复用旧测试轮次的库。

切换到工具所在目录。先通过现有安全方式设置以下变量；不要把密码或真实凭证写进本文档。

03全量扫描：整个 100GiB 只扫一次

先数对象，不写进度库

./limewire-purge scan "${purge_common[@]}" --count-only

计数应与测试名单相符。为 0 时先检查 bucket 名称/ID 和 BSDB 同步，不要继续；“0 个对象”不能当作清理已完成。

确认后，全量入库并封存

./limewire-purge scan "${purge_common[@]}" --batch 5000
./limewire-purge status "${purge_common[@]}"

预期：scan status=COMPLETE，对象数大于 0，Σ payload_size 约为 100GiB。--batch 5000 仅指数据库每页读取行数，不是删除子任务大小。

扫描失败可重跑 scan；封存成功后不再重复 scan。此后所有 10GiB 子任务都从这份名单分配。

04第一批：创建约 10GiB → 删除；验收可后置

以下按已完成 QA 小规模验证的情况举例；首次回归建议先改成 1GiB、最多 2 个对象。命令分段执行，不要整页一次粘贴运行。

A. 创建本批，人工核对摘要

./limewire-purge task create "${purge_common[@]}" \
  --target-size 10GiB --max-objects 10000

./limewire-purge status "${purge_common[@]}"

核对 task=N、objects、logical_bytes 和环境绑定。create 不删数据。如果已有首次删除未完成的任务，重复 create 返回它；只有待验收任务时，可以分配下一批。

B. 确认本批范围后，正式删除

为本次执行创建独立日志目录；重跑时也新建目录，避免覆盖上次错误证据。

purge_log_dir="./purge-logs/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$purge_log_dir"

./limewire-purge purge "${purge_common[@]}" \
  "${purge_chain[@]}" "${purge_storage[@]}" \
  --execute --concurrency 1 --qps 5 --max-retry 10 \
  2>&1 | tee "$purge_log_dir/purge.log"

只有 --execute 才真实删除。默认处理当前唯一待删除批次，不需要每次手记 ID。--task-id N 可固定已核对的批次，也可显式补删旧的未验收批次；已 DONE 的任务禁止直接 purge。不会自动选择旧批次补删。

purge 报错就先停在这里。根据日志排障后重跑；不要直接创建下一批，也不要把“某些 key 已删除”当成本批完成。

C. 独立验收：可现在做，也可删完多批再做

本批 purge 成功后，就可以回到 A 创建下一批，不必先运行下面的 verify。默认 verify 每次只验收最早一批删除已完成、尚未验收完成的任务，不是最近一批；指定批次时加 --task-id N。小规模 QA 建议仍先验收再扩大。

./limewire-purge verify "${purge_common[@]}" \
  "${purge_storage[@]}" --qps 5 \
  2>&1 | tee "$purge_log_dir/verify.log"

./limewire-purge status "${purge_common[@]}"

verify 检查选中批次的 s<oid>_、e<oid>_ 及本地元数据，默认报告为 residue-task-ID.tsv。成功退出并打印 state=DONE 后，验收完成批数增加；其他待删除 / 待验收任务仍保留。每次执行前可新建日志目录避免覆盖日志。

DONE_WITH_EXCEPTIONS 表示有人工延期对象，不等于全部清干净。没有延期项的正常流程才按下面的“约 10 批”继续。status 只展示已记录的结果，不能代替 verify 的实际复查。完整判断规则见命令分工与状态表。

不要写死“循环 10 次”。容量是近似值，还有对象数上限和超大对象。按 status 的未分配数与验收结果推进；create 提示“无未分配对象”时，再检查延期池和最终状态，而不是仅凭这条提示结束。

06失败了，怎么接着跑？

看到什么下一步操作
purge：!!! STOP查看 task、OID、错误原因。普通失败停止新对象，等待在途对象完成或失败并尽量落库。排障后重跑第 04-B 节的 purge 命令；不需 task resume。
Ctrl+C / 进程退出确认旧进程已退出；使用原进度库、原当前任务重跑 purge。已完成项跳过，失败/未完成项按实际残留继续。
verify：ERROR / 中断排障后重跑 verify。当前实现会记录普通查询错误并继续验收；下一次跳过本代次已 PASS 的项。
verify：RESIDUE用 purge --execute --task-id N 补删该批，再 verify --task-id N；旧验收代次失效，整批重验。不阻塞后续批次分配，不能用默认 purge 误选下一批。
SAFETY_HOLD身份、名单或 key 安全异常。任一批暂停都会阻止继续创建和删除；核对后 task resume --task-id N 写明依据。后续仍会重新检查，不能靠切换批次绕过。
同一 OID 长期失败先查原因，不要反复盲跑。必要时人工 task defer，记录原因和后续安排；该项不计 PASS，留在延期池。

重试边界：piece 默认首次尝试 + 10 次重试；链查询、SpDB 临时错误最多 3 次应用层尝试，间隔 1 秒/2 秒。权限等永久错误不盲目重试。普通失败收尾可能较久；安全异常、失锁、Ctrl+C 仍立即取消。

特殊情况命令：解除安全暂停 / 延期 / 重新处理延期项

仅在查明原因并获得相应操作确认后使用。示例 OID 123 必须换成实际目标；不适用于普通网络失败。

# 仅用于确有安全暂停、且已查清处理依据的任务
./limewire-purge task resume "${purge_common[@]}" \
  --reason '填写实际排查结果和恢复依据'

# 延期一个确实暂时无法处理的对象：不删除、不算 PASS
./limewire-purge task defer "${purge_common[@]}" --oid 123 \
  --reason '填写失败原因、延期依据和后续安排'

# 当前批删除处理结束后，即可显式创建任务处理延期池（不必等原批验收）
./limewire-purge task create "${purge_common[@]}" \
  --retry-deferred --target-size 10GiB --max-objects 10000

07什么情况下可以说“本 SP 清理完成”？

最终检查

./limewire-purge status "${purge_common[@]}"
  • 扫描名单 COMPLETE 且非空，至少有一个已完成任务。
  • unassigned=0、deferred_unresolved=0，没有未完成任务和执行锁。
  • status 打印 ALL_DONE；检查另一个 bucket 的对照对象仍可读取且内容摘要一致。
  • 保留代码版本、任务摘要、每批日志和 verify 报告；不要把凭证放进验收材料。
完成范围仅限本次配置的本 SP 物理桶与本地元数据。其他 SP 要分别执行和验收；开启显式版本桶放行时，历史版本不在范围内。verify 能证明目标当前数据无残留，不能单独证明没有误删其他数据，也不代表链上对象已删除或停止计费。不要因为工具结束就直接恢复挑战服务。

08purge、verify、status 分别做什么？

命令实际动作结果
purge检查链上归属与对象快照，删除物理数据和本地元数据逐 OID 记录结果；本批删除成功记 purged_at，允许下一批；不等于验收通过
verify实际访问存储与 SpDB，重新检查两个前缀和本地元数据是否残留记录 PASS / RESIDUE / ERROR；满足条件后结束本批
status只查询进度库及 MySQL 执行锁，不查链、不扫描 S3显示当前进度和已保存的验收结论，不产生新的验收结果
purge 可逐批往前推进，verify 可以稍后逐批复查，status 只查询结果。ALL_DONE 仅用于最终收尾，不是下一批删除的门槛；不必每批反复执行 status。

status 不是新命令：第一版 bba4983 已有；9beec7b 子任务改造增加了子任务状态、延期池及 ALL_DONE 判断。

判断依据：本 SP 的独立进度库

以下表均位于 --progress-dsn 指定的数据库，不是业务 BSDB / SpDB 的原始表。

表关键字段 / 用途

对象统计由 task_objects 关联 purge_tasks 和 purge_progress 得出。MySQL IS_USED_LOCK() 返回的连接必须匹配该任务记录的连接，才算本批运行；不能把所有排队批次都标为运行中。多次查询不是原子快照，显示可能短暂变化。

什么时候写入 done_at？

verify 收尾时要求：任务成员数与冻结数量一致、非延期对象无未处理或删除失败项，且本代次 PASS 数 + 延期数 = 本批总数。任务还必须没有安全暂停、处于对应验收阶段，才写入 purge_tasks.done_at。

purge_progress.status=1 是逐对象删除成功；purged_at 是整批删除里程碑，允许下一批；done_at 才是本批验收结束。旧批次补删保留 purged_at，不重新阻塞新批，但会使旧验收失效，必须重新验收。

升级已有进度库：第一次正常写命令在持锁时自动补列，并为已处理完的旧批次补 purged_at，不补写 PASS / done_at。status 只读，不执行表升级；不要混用新旧二进制操作同一进度库。

ALL_DONE 是全局汇总，不是单个任务的状态字段

默认 status 同时满足以下条件才打印 ALL_DONE：名单已绑定、扫描 COMPLETE 且非空、至少有一个完成子任务、未分配数为 0、未解决延期数为 0、无未完成子任务、无执行锁。这是数据库中已记录的完成结论，不是当场重新检查 S3。

status 默认展开当前待删除批次和所有待验收批次；stages 分别统计 deletion_completed / deletion_pending / verification_completed / verification_pending。删除完成数是历史里程碑，不代表补删也已成功。历史已验收任务体现在汇总计数中；查看某一批的 DONE 时指定 ID：

# 整体进度：当前任务、完成批数、未分配 / 延期池、ALL_DONE
